# PRD：购物清单单页应用 v1

> 本 PRD 由 grill-me 需求审问会议收敛、to-prd 综合生成（2026-06-10）。
> 对应 issue 见本仓库 issue tracker；后续由 to-issues 拆分为带 L1–L4 验收标准的开发包。

## 问题陈述

去超市购物前，我会在脑子里或随手的便签上记要买的东西，但便签容易丢、改起来乱：
买到一半想划掉已经拿到的东西、临时想加一件、发现数量记错了要改，纸面上很快变得不可读。
我需要一个打开即用的购物清单页面：能加、能改、能勾掉已购的，购物中单手操作手机也方便。

## 解决方案

一个单页购物清单应用。打开页面看到一份清单：未买的在上、已购的沉底划线。
在顶部输入框输入名称（可选数量）回车即添加；每行可勾选「已购」、行内编辑名称/数量、
直接删除；顶部「全部 / 待购 / 已购」三个标签页筛选视图，并显示「共 N 项 · 已购 M 项」；
一键「清除已购」清空买完的部分。所有数据存在服务端 SQLite 里，刷新、重启都不丢。
界面全中文，375px 手机宽度下单列布局可正常操作。

## 实现决策

**模块划分**（四个模块，两深两浅）：

- **数据访问模块（store）**——深模块。封装全部 SQLite 细节：建表、增删改查、按状态筛选、
  清除已购、排序。接口形如 `createStore(dbPath)` 返回
  `{ list(filter), add(name, quantity), update(id, patch), remove(id), clearPurchased() }`；
  传入 `:memory:` 即得到隔离测试实例。SQL 不外漏。
- **校验模块（validation）**——深模块。纯函数 `validateItemInput({ name, quantity })`，
  通过返回规范化结果，失败返回中文错误消息。规则集中一处：名称去除首尾空白后 1–50 字符，
  数量为 1–99 的整数。
- **HTTP API 层**——浅层。Express 路由把 REST 端点接到 store + validation，并提供前端静态文件。
- **前端单页**——原生 HTML/JS，无构建步骤。通过 fetch 调用 API，按状态渲染。

**数据模型**（item）：

- `id`：自增整数主键
- `name`：文本，1–50 字符（去首尾空白后）
- `quantity`：整数 1–99，默认 1
- `purchased`：布尔，默认 false
- `created_at`：创建时间戳

单一隐式清单，无多清单概念。允许重复名称。

**排序规则**：已购沉底、组内最新在前——`ORDER BY purchased ASC, created_at DESC, id DESC`。
勾选已购时该行从待购区移动到已购区顶部。

**API 契约**：

- `GET /api/items?filter=all|active|purchased`——返回排序后的项目数组；`filter` 省略等同 `all`
- `POST /api/items`——body `{ name, quantity? }`；成功 `201` + 完整 item；校验失败 `400`
- `PATCH /api/items/:id`——body 为 `name` / `quantity` / `purchased` 的任意子集；成功 `200` + 更新后 item；校验失败 `400`；不存在 `404`
- `DELETE /api/items/:id`——成功 `204`；不存在 `404`
- `DELETE /api/items?purchased=true`——批量删除全部已购项，返回 `200` + `{ "deleted": N }`
- 错误响应统一为 `{ "error": "中文消息" }` 单字段结构，前端直接渲染为行内错误文案

**交互决策**：

- 界面语言：全中文（按钮、空状态、错误文案、统计）
- 编辑：每行「编辑」按钮切换行内编辑态（输入框 + 保存/取消），不用双击、不用弹窗
- 删除：单项删除立即生效，无二次确认
- 校验错误：行内红色提示，不用 toast、不用 alert
- 筛选在服务端实现（`?filter=` 参数），前端切换标签页时重新请求

**并行开发安全**（多 agent 并行实现切片时的约束）：

- 服务端口读 `PORT` 环境变量（默认 3000），并行做浏览器验证时各用独立端口
- 测试一律使用 `:memory:` 数据库，开发库文件不入库

## 测试决策

- **好测试的标准**：只断言外部可观察行为（HTTP 状态码、响应体、列表顺序、错误消息文案），
  不断言内部实现（不查 SQL 语句、不窥探模块私有状态）。测试失败应当意味着用户可感知的行为变了。
- **API 集成测试为主**：用 supertest 直接打真实 Express 应用（挂 `:memory:` store），
  覆盖全部端点的成功路径、校验失败路径、404 路径、排序与筛选行为。store 模块经由 API 测试
  间接覆盖，不另写重叠的单测。
- **校验模块单测**：纯函数直接测边界组合——空名称、纯空白名称、50/51 字符、数量 0/1/99/100/小数。
- **前端不写单元测试**：UI 行为由浏览器级验收（L3 截图证据）覆盖。
- **先例**：仓库为新项目，无既有测试可参照；测试风格以本 PRD 为准（Vitest + supertest）。
